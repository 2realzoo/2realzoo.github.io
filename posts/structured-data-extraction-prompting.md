# 프롬프트를 잘 쓰는 법: LLM에게 정형 데이터를 뽑게 할 때 배운 것

LLM을 업무 시스템에 붙이다 보면 자연스럽게 이런 요구가 생깁니다.

> 사용자가 자연어로 입력한 문장에서 필요한 값을 뽑아서 정해진 필드에 넣고 싶다.

예를 들면 이런 작업입니다.

- 날짜나 시간 정보 추출
- 사람, 장소, 제품, 주제 같은 엔티티 추출
- 핵심 내용과 부가 내용 분리
- 미래 일정인지, 이미 완료된 기록인지 구분
- 특정 필드에 저장할 수 있는 값인지 판단
- 결과를 JSON이나 스키마에 맞는 형태로 반환

처음에는 꽤 단순해 보입니다. 프롬프트에 “이런 값은 이렇게 뽑고, 저런 값은 무시하라”고 적으면 될 것 같습니다.

하지만 실제 업무 데이터로 테스트해보면 생각보다 금방 복잡해집니다. 문장은 짧고, 표현은 생략되어 있고, 하나의 문장 안에 여러 정보가 섞여 있습니다. 사람은 쉽게 이해하지만, 시스템 입장에서는 그 값을 어느 필드에 넣어야 하는지 명확하지 않은 경우가 많습니다.

이번에 정형 데이터 추출 프롬프트를 다루면서 배운 가장 큰 교훈은 이것이었습니다.

> 좋은 프롬프트란 LLM에게 더 많은 판단을 시키는 프롬프트가 아니라, LLM이 판단해야 할 범위를 줄여주는 프롬프트다.

---

## 처음에는 프롬프트를 더 자세히 쓰려고 했다

처음 접근은 일반적인 프롬프트 개선이었습니다.

기존 프롬프트에는 이미 많은 규칙이 들어 있었습니다.

- 이 표현이 나오면 값을 추출하라
- 저 표현은 무시하라
- 특정 조건에서는 절대 추출하지 말라
- 특정 필드는 반드시 이런 형식으로 반환하라
- 예외 상황에서는 이런 값을 사용하라

문제가 생길 때마다 규칙을 추가하다 보니 프롬프트는 점점 길어졌습니다. 중요한 부분을 강조하기 위해 `반드시`, `절대`, `중요`, `주의` 같은 표현도 많아졌습니다. 비슷한 규칙이 여러 번 반복되기도 했습니다.

겉으로 보기에는 안전해 보입니다. 하지만 실제로는 반대였습니다.

프롬프트 안에 규칙이 많아질수록 LLM은 더 많은 판단을 한 번에 해야 했습니다.

- 이 표현이 실제 값인지
- 단순 참고 정보인지
- 과거에 완료된 일인지
- 미래 일정인지
- 날짜만 있는지
- 시간만 있는지
- 둘 다 있는지
- 값이 없으면 기존 값을 유지해야 하는지
- 빈값으로 둬야 하는지
- 추론해서 채워도 되는지

즉, 프롬프트는 자세해졌지만 LLM의 부담은 줄어들지 않았습니다. 오히려 “모든 예외를 LLM이 알아서 판단해야 하는 구조”가 되었습니다.

---

## 강조가 많다고 좋은 프롬프트는 아니었다

프롬프트를 만들다 보면 중요한 규칙을 강조하고 싶어집니다.

그래서 이런 식의 문장이 늘어납니다.

- 절대 이렇게 하지 마라
- 반드시 이렇게 해라
- 이 규칙이 가장 중요하다
- 아래 조건을 어기면 안 된다
- 다시 한 번 강조한다

물론 강조가 필요한 순간은 있습니다. 하지만 강조가 많아지면, 모델 입장에서는 무엇이 진짜 우선순위인지 흐려질 수 있습니다.

특히 정형 데이터 추출에서는 강조보다 중요한 것이 있습니다.

1. 출력해야 할 필드가 무엇인지
2. 각 필드의 타입이 무엇인지
3. 값이 없을 때 어떻게 해야 하는지
4. 추론 가능한 값과 추론하면 안 되는 값의 경계가 무엇인지
5. 후보가 여러 개일 때 어떤 것을 우선해야 하는지
6. 애매하면 값을 채울지, 비울지, 낮은 confidence로 둘지

즉, 강조 문구를 추가하는 것보다 **판단 기준을 구조화하는 것**이 더 중요했습니다.

OpenAI의 Structured Outputs 문서도 이 지점과 맞닿아 있습니다. 단순히 “JSON으로 답하라”고 하는 것과, JSON Schema로 필드·타입·enum·필수값을 제한하는 것은 다릅니다. 전자는 형식 요청에 가깝고, 후자는 모델이 낼 수 있는 출력 공간 자체를 줄이는 일에 가깝습니다.

---

## 문제는 “프롬프트 길이”가 아니라 “책임 범위”였다

정형 데이터 추출 프롬프트가 흔들리는 이유는 단순히 프롬프트가 짧아서가 아니었습니다. 문제는 하나의 프롬프트가 너무 많은 책임을 가지고 있다는 점이었습니다.

예를 들어 하나의 LLM 호출에 이런 일을 모두 맡기면 어떻게 될까요?

- 문장에서 시간 표현 찾기
- 날짜 표현 찾기
- 상대 날짜 해석하기
- 문장이 완료된 행동인지 판단하기
- 미래 일정인지 판단하기
- 대상자 이름 찾기
- 핵심 정보와 부가 정보 분리하기
- 최종 저장할 값을 완성하기
- 값이 없을 때 fallback까지 결정하기

이건 사람에게도 꽤 복잡한 일입니다. 그런데 LLM에게 한 번에 맡기면, 어느 한 부분이 흔들릴 때 전체 출력이 흔들립니다.

그래서 관점을 바꿨습니다.

> 이 판단을 꼭 LLM이 해야 할까?

이 질문을 기준으로 업무를 다시 나눠봤습니다.

---

## LLM이 할 일과 시스템이 할 일을 나누기

정형 데이터 추출에서 LLM이 잘하는 일은 자연어를 이해하는 것입니다.

예를 들면 이런 판단입니다.

- 이 문장에 날짜 신호가 있는가?
- 시간 신호가 있는가?
- 이 표현은 완료된 행동에 가까운가?
- 이 문장은 미래 일정에 가까운가?
- 이 값은 특정 필드 후보로 볼 수 있는가?

반대로 시스템이 더 잘하는 일도 있습니다.

- 허용 가능한 날짜 범위 계산
- 후보 날짜 목록 생성
- 날짜와 시간 조합
- enum 검증
- 타입 검증
- 필수 필드 확인
- 값이 범위를 벗어났는지 확인
- 값이 없을 때 fallback 처리
- confidence 기준으로 반영 여부 결정

이런 것까지 LLM에게 맡기면 프롬프트가 복잡해집니다. 그리고 프롬프트가 복잡해질수록 모델은 더 많은 규칙을 동시에 해석해야 합니다.

그래서 더 나은 방향은 이렇습니다.

> LLM은 자연어에서 신호를 뽑고, 시스템은 그 신호를 검증하고 조합한다.

예를 들어 LLM에게 최종 값을 한 번에 만들게 하는 대신, 먼저 신호를 분리하게 할 수 있습니다.

- 날짜 신호가 있는지
- 시간 신호가 있는지
- 날짜와 시간이 모두 있는지
- 둘 다 없는지
- 완료된 행동인지
- 미래 일정인지

그 다음 최종 값 생성은 시스템이 맡습니다.

이렇게 하면 LLM은 “모든 정책을 외워서 최종 정답을 만드는 역할”이 아니라, “문장에서 필요한 신호를 찾는 역할”에 집중할 수 있습니다.

---

## 프롬프트만으로 해결하려 하면 정책이 계속 쌓인다

실제로 정형 데이터 추출 문제를 다루다 보면 이런 상황이 자주 생깁니다.

처음에는 단순히 “시간을 뽑아줘”였는데, 곧 이런 예외가 붙습니다.

- 날짜만 있으면 어떻게 할 것인가?
- 시간만 있으면 어떻게 할 것인가?
- 날짜와 시간이 모두 있으면 어떻게 할 것인가?
- 아무것도 없으면 기존 값을 유지할 것인가?
- 미래 일정은 제외할 것인가?
- 과거 기록과 미래 일정이 동시에 있으면 무엇을 우선할 것인가?
- 상대 날짜 표현은 어디까지 허용할 것인가?
- 요일 표현은 어떤 기준으로 해석할 것인가?

이 모든 걸 프롬프트에 계속 추가하면 단기적으로는 해결되는 것처럼 보입니다. 하지만 장기적으로는 프롬프트가 정책 문서처럼 변합니다.

문제는 LLM이 정책 엔진이 아니라는 점입니다. 정책이 많아질수록 작은 표현 차이에 따라 결과가 달라질 수 있습니다.

그래서 프롬프트에 규칙을 계속 쌓는 대신, 다음처럼 나누는 편이 낫습니다.

- LLM: 문장 안에 어떤 신호가 있는지 판단
- 시스템: 그 신호를 어떤 정책으로 최종 값에 반영할지 결정

이렇게 하면 정책 변경도 쉬워집니다. 프롬프트 전체를 다시 튜닝하는 대신, 후처리 규칙이나 검증 로직을 바꾸면 되기 때문입니다.

---

## 업무 단위도 쪼개는 편이 낫다

같은 이유로 하나의 큰 LLM 호출보다 작은 업무 단위로 쪼개는 방식이 더 안정적일 수 있습니다.

예를 들어 하나의 요청에서 모든 필드를 한 번에 추출하게 하는 대신, 성격이 다른 작업을 나눌 수 있습니다.

- 기본 정보 추출
- 시간 정보 추출
- 일정 정보 추출
- 이름/엔티티 추출
- 핵심 내용 요약
- 부가 정보 분류
- 최종 검증

이렇게 나누면 각 프롬프트는 짧아지고, 각 모델 호출의 책임도 명확해집니다.

또한 독립적인 작업은 병렬로 처리할 수 있습니다. 정형 데이터 추출에서는 모든 작업이 순차적으로 실행될 필요가 없습니다.

예를 들어 “완료된 기록에서 필요한 값을 찾는 작업”과 “미래 일정으로 볼 수 있는 표현을 찾는 작업”은 같은 원문을 보더라도 서로 다른 목적을 가진 작업입니다. 이 둘을 하나의 프롬프트 안에서 동시에 판단하게 만들 수도 있지만, 분리해서 병렬로 실행하면 각 작업의 기준을 더 명확하게 만들 수 있습니다.

이 구조의 장점은 세 가지입니다.

1. 각 프롬프트가 단순해집니다.
2. 실패 지점을 찾기 쉬워집니다.
3. 작업 성격에 따라 다른 모델을 선택할 수 있습니다.

---

## 모든 작업에 큰 모델이 필요한 것은 아니다

정형 데이터 추출을 쪼개다 보면, 모든 단계가 복잡한 추론을 요구하지 않는다는 걸 알게 됩니다.

어떤 단계는 단순 분류에 가깝습니다.

- 이 문장에 시간이 있는가?
- 이 표현은 날짜인가?
- 값이 enum 중 하나에 해당하는가?
- confidence가 충분한가?
- 특정 필드를 채울 수 있는가?

이런 작업은 큰 모델이 아니어도 충분히 잘할 수 있습니다. 오히려 작은 모델을 쓰는 편이 비용과 속도 면에서 유리할 수 있습니다.

그래서 업무 단위를 나눈 뒤에는 각 단계에 맞는 모델을 선택할 수 있습니다.

- 복잡한 문맥 이해가 필요한 단계: 더 강한 모델
- 단순 추출, 분류, 형식화 단계: mini 또는 nano 계열 모델
- 후처리 가능한 정책 판단: 시스템 로직

이렇게 하면 전체 시스템은 더 빠르고 저렴해집니다. 무엇보다 “큰 모델 하나에게 모든 걸 맡기는 구조”보다 운영상 설명하기 쉽습니다.

---

## 정형 데이터 추출 프롬프트의 기본 원칙

이번 경험을 바탕으로 정리하면, LLM에게서 정형 데이터를 뽑을 때는 아래 원칙이 유용했습니다.

### 1. 출력 스키마를 먼저 정한다

프롬프트보다 먼저 정해야 할 것은 출력 구조입니다.

- 어떤 필드를 반환할 것인가?
- 각 필드의 타입은 무엇인가?
- 값이 없으면 빈 문자열인가, null인가?
- 가능한 값이 정해져 있는가?
- 필수 필드와 선택 필드는 무엇인가?
- confidence가 필요한가?

출력 구조가 불명확하면 프롬프트가 아무리 좋아도 결과가 흔들립니다.

### 2. LLM에게 최종 결정을 모두 맡기지 않는다

LLM에게 “최종 값을 알아서 만들어줘”라고 하면 편합니다. 하지만 정형 데이터 추출에서는 이 방식이 위험할 수 있습니다.

최종 값은 여러 정책의 결과일 때가 많습니다.

- 기존 값 유지
- 새 값으로 교체
- 일부만 수정
- 범위 밖이면 무시
- 미래 값이면 제외
- 값이 없으면 fallback

이런 정책은 가능하면 시스템에서 처리하는 편이 낫습니다.

### 3. 프롬프트는 신호 추출에 집중시킨다

프롬프트의 역할을 줄이면 더 안정적입니다.

좋은 질문은 이런 식입니다.

- 이 문장에 날짜 신호가 있는가?
- 이 문장에 시간 신호가 있는가?
- 이 값은 완료된 행동을 가리키는가?
- 이 값은 미래 일정인가?
- 이 필드는 채울 수 있는가?
- 확신할 수 없다면 비워야 하는가?

반대로 좋지 않은 질문은 이런 식입니다.

- 모든 문맥을 고려해서 최종 저장값을 완성하라.
- 예외 상황까지 알아서 판단하라.
- 값이 없으면 적절히 추론하라.
- 기존 값과 새 값을 알아서 조합하라.

후자는 모델에게 너무 많은 자유도를 줍니다.

### 4. 예시는 실제 실패 케이스를 닮아야 한다

few-shot 예시는 중요합니다. 하지만 예시가 많다고 항상 좋은 것은 아닙니다.

좋은 예시는 실제로 모델이 헷갈리는 상황을 포함해야 합니다.

- 값이 명확한 케이스
- 값이 없는 케이스
- 비슷하지만 추출하면 안 되는 케이스
- 여러 후보가 섞인 케이스
- 날짜만 있는 케이스
- 시간만 있는 케이스
- 미래 일정과 과거 기록이 함께 있는 케이스
- 애매해서 빈값으로 둬야 하는 케이스

예시는 모델에게 “정답 패턴”을 보여주는 동시에, “하지 말아야 할 추론의 경계”를 알려줍니다.

Anthropic의 프롬프트 가이드에서도 예시는 실제 사용 사례와 가까워야 하고, 다양한 edge case를 포함해야 하며, 3~5개의 잘 구성된 예시가 출력 일관성에 도움이 된다고 설명합니다.

### 5. 금지 규칙보다 긍정 규칙을 우선한다

“하지 마라”는 규칙만 많으면 모델은 여전히 무엇을 해야 하는지 헷갈릴 수 있습니다.

예를 들어:

> 미래 일정은 추출하지 마라.

보다 더 좋은 방식은:

> 완료된 행동을 나타내는 시간만 추출한다. 예정, 계획, 다음 방문, 후속 미팅처럼 미래 행동을 나타내는 시간은 제외한다.

즉, 금지보다 기준을 명확히 주는 편이 낫습니다.

### 6. 검증과 재시도를 프롬프트 밖에 둔다

LLM 출력은 항상 검증해야 합니다.

- JSON Schema 검증
- 타입 검증
- 필수 필드 검증
- enum 검증
- 날짜 범위 검증
- confidence 검증
- 비즈니스 규칙 검증

검증에 실패하면 재시도하거나, 값을 비우거나, fallback을 적용할 수 있습니다. 이 과정을 프롬프트 안에 모두 넣으려고 하면 복잡해집니다.

정형 데이터 추출은 프롬프트 하나로 끝나는 작업이 아니라, 작은 파이프라인으로 보는 편이 맞습니다.

```text
입력
→ 전처리
→ 작업 분기
→ LLM 신호 추출
→ 스키마 검증
→ 정책 기반 후처리
→ 최종 반영
```

Instructor 같은 라이브러리가 Pydantic 모델, validation, retry를 함께 강조하는 이유도 여기에 있습니다. 정형 데이터 추출은 “모델이 예쁘게 JSON을 쓰게 하는 일”이 아니라, 타입과 검증을 포함한 파이프라인을 만드는 일에 가깝습니다.

## “프롬프트 잘 쓰기”의 의미가 바뀌었다

처음에는 프롬프트를 잘 쓴다는 것이 더 자세히 설명하는 것이라고 생각했습니다. 하지만 정형 데이터 추출을 다루면서 생각이 바뀌었습니다.

프롬프트를 잘 쓴다는 것은 모델에게 많은 규칙을 외우게 하는 것이 아닙니다. 모델이 판단해야 할 것을 작게 만들고, 판단하지 않아도 되는 것은 시스템이 미리 처리해주는 것입니다.

즉, 좋은 프롬프트는 길고 강한 프롬프트가 아닙니다.

좋은 프롬프트는:

- 입력과 출력이 명확하고
- 모델의 책임이 작고
- 예외가 구조화되어 있고
- 애매한 경우의 처리 기준이 있으며
- 검증 로직과 잘 연결되는 프롬프트입니다.

---

## 결론

LLM으로 정형 데이터를 뽑을 때 가장 위험한 말은 “알아서 잘 뽑아줘”입니다.

데모에서는 잘 동작할 수 있습니다. 하지만 실제 업무 데이터에서는 표현이 짧고, 생략이 많고, 여러 정보가 한 문장에 섞입니다. 이때 LLM에게 모든 판단을 맡기면 결과가 흔들립니다.

이번에 얻은 교훈은 단순했습니다.

> LLM이 결정할 일은 최대한 줄이고, 시스템에서 미리 분기할 수 있는 부분은 먼저 분기한다.

프롬프트는 모든 비즈니스 로직을 담는 장소가 아닙니다. 프롬프트는 LLM이 자연어를 이해해 필요한 신호를 찾도록 돕는 인터페이스입니다.

정형 데이터 추출의 안정성은 프롬프트 하나에서 나오지 않습니다. 스키마, 작업 분리, 병렬 처리, 모델 선택, 검증, 후처리가 함께 맞물릴 때 나옵니다.

그래서 프롬프트를 잘 쓰는 가장 현실적인 방법은 역설적으로 이것입니다.

> 프롬프트가 해야 할 일을 줄이는 것.
